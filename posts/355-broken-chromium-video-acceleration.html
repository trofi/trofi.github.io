Broken chromium video acceleration

November 22, 2026
#amd, #bug, #chromium, #polaris, #wayland

Tl;DR

mesa-26.3.0 broke chromium video acceleration on wayland on at least AMD GFX8 chips (mine is polaris12). The easiest workaround is to roll back mesa before "radeonsi: Support DRM format modifiers on GFX6-8" commit. chromium has a proposed fix for inclusion upstream.

More Words

The Problem: Lost GPU Acceleration In chromium

Somehow I did not reboot my machine for a while. Once I had a chance to do it I noticed that chromium browser took tens of seconds to start (normally expected to start in a second). The scroll was sluggish. Checking chrome://gpu/ I found that video acceleration was disabled. stderr complained about exit code 132 (SIGILL) in GPU process:

What Triggered the Regression?

I was a bit confused as most other OpenGL programs worked just fine. Why the chromium is special here? To restore my browser I attempted to pinpoint the component. I keep 90 days of past OS system builds and build the systems every night. I had 50 generations to bisect through. After 7 reboots I found that November 10 version was fine while November 11 version was not. From the system generations I extracted nixpkgs commits my system was built from (nixos-version has it as is as last 6 characters):

I was not sure where the bug is: in niri, in mesa, in chromium or maybe in linux kernel GPU in how it handles other modes? Looking around mesa bug tracker I found "[radeonsi/GFX6] Regression 26.2.6 → 26.3.1: Chromium-based browser GPU process dies with SIGILL on Oland [1002:6613]; downgrading Mesa fixes it" bug which looks identical to mine. A mystery! I reported my setup in the comment. And day later someone reported that chromium already has the fix proposed for inclusion:

[PATCH] [ozone] Don't range-check DRM modifier halves as EGLint

NativePixmapEGLBinding::InitializeFromNativePixmap() pushed the low
and high 32 bits of the format modifier through
base::checked_cast<EGLint>(), which CHECK-fails when a half has bit 31
set. AMD GFX8 (Polaris) modifiers from recent Mesa, such as
0x02000001D0CA0400, hit this and crash the GPU process.

EGL_EXT_image_dma_buf_import_modifiers expects the raw bit pattern of
each half, so reinterpret the uint32_t halves as EGLint with
base::bit_cast instead. Offsets keep the checked conversion.

More Targeted Workaround

To restore video acceleration without full rollback of mesa I settled on a single patch revert in my local system via this overlay definition:

# cat /etc/nixos/overlay.nix
final: prev: {
  mesa = prev.mesa.overrideAttrs(oa: {
    patches = oa.patches ++ [
      # fix chrome hwaccel
      (prev.fetchpatch {
        name = "revert-AMD_UNKNOWN_MODIFIER.patch";
        url = "https://gitlab.freedesktop.org/mesa/mesa/-/commit/12b7b819edb4ddd3580e7e5ffe384610ae726c90.patch";
        revert = true;
        hash = "sha256-VJAaqgbjlfhjg++2DjG1ZXrE6o7HnZrToJBCPEBAPks=";
      })
    ];
  });
}

Another option would be to apply pending chromium patch, but nixpkgs does not make it easy and chromium builds are quite long.

Where Do These Modes come From?

0x0000000000000000 = LINEAR and 0x00ffffffffffffff = INVALID are just two constants. But AMD_UNKNOWN_MODIFIER has many different values:

0x02000001c90a6400 = AMD_UNKNOWN_MODIFIER
0x02000001c90a4400 = AMD_UNKNOWN_MODIFIER
0x02000001c90a0400 = AMD_UNKNOWN_MODIFIER
0x0200000000004200 = AMD_UNKNOWN_MODIFIER
0x0200000000000200 = AMD_UNKNOWN_MODIFIER

I was wondering why AMD(TILE_VERSION = unknown, TILE = unknown) (0x02000001d08a0400) does not show any details about TILE_VERSION / TILE and found that libdrm did not yet merge support for it at "amdgpu: Print new DRM format modifiers for AMD GFX6-8". The header change has a good description of bits:

 * DRM format modifier fields on AMD GPUs:
 *     7:0 TILE_VERSION             Values are AMD_FMT_MOD_TILE_VER_*
 *    12:8 TILE                     Values are AMD_FMT_MOD_TILE_<version>_*
 *      13 DCC                      Delta Color Compression, supported on GFX8 and newer
 *   55:14 (chip specific)          See below for details, depends on GFX block version
 *   63:56 Vendor                   Value is DRM_FORMAT_MOD_VENDOR_AMD
...
 * Chip specific fields on Gfx6-8:
 *   16:14 MICROTILE                Micro tile format
 *   21:17 PIPE_CONFIG              Number of pipes and how pipes are interleaved
 *   24:22 TILE_SPLIT               Tile split size
 *   26:25 BANK_WIDTH               Number of tiles in the X direction in the same bank
 *   28:27 BANK_HEIGHT              Number of tiles in the Y direction in the same bank
 *   30:29 MACRO_TILE_ASPECT        Macro tile aspect ratio
 *   32:31 NUM_BANKS                Number of banks
 *   55:33 -                        Reserved for future use, must be zero

Parting Words

Timur Kristóf is busy updating Linux ecosystem to expose to compositors various tiling modes available on older AMD GPU cards like my radeonsi (GFX8). This commit message is a great overview of the motivation behind the changes and overview of some limitations. That's very exciting! As these changes slowly trickle into released versions of software it exposes bugs on the software. In this case it was a chromium bug.

Reverting "radeonsi: Support DRM format modifiers on GFX6-8" in mesa allowed me to restore GPU acceleration in chromium. I suspect using the old kernel would also work around the failure. I did not test the chromium fix yet, but it looks like it should work as well.
